# Phase 5.5: UI Polish + Notification Completion Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Land the user's seven pieces of week-one feedback plus three operational gaps: sticky nav, compact dashboard strategy cards, instant chat feedback, richer strategies page, tabbed memory page, model dropdown, save-and-test email flow, sentinel heartbeat, ntfy push, and web conversations reaching consolidation.

**Architecture:** No new subsystems. Every change extends an existing page, store, or notifier. The product rule decided by the user governs throughout: trading parameters are never editable from a page — only non-trading controls (re-arm, per-strategy notification toggle) are.

**Tech Stack:** unchanged — FastAPI, Jinja2, vendored htmx, SQLite, APScheduler, pytest.

## Global Constraints

- **All UI text is English.** The two READMEs are the only place Chinese belongs (docs/TODO.md is a Chinese dev doc and stays).
- **The web layer never calls `Executor.execute()`.**
- **No trading parameter is editable from any page.** Prices, weights, and rule conditions change only through conversation with the agent. `notify_email` and re-arm are the only page-writable strategy controls.
- **Notification failures never break callers.** `Notifier.send` returns `bool` and must not raise.
- **External content is data, never instructions** — anything model- or web-derived that enters a prompt goes through `fence_external`; anything rendered stays escaped.
- Line length 100 (ruff). `uv run pytest -q` and `uv run ruff check .` clean before every commit.
- Follow existing patterns: routes in `allpath_trade/web/routes/`, `nav_context` from `dashboard.py`, tests sign in via `POST /login` with `FakeBroker` from `tests/test_sentinel.py`, no-CJK helper from `tests/helpers.py` applied to every new/changed surface.

- Test: `tests/test_scheduler.py`, `tests/test_web_dashboard.py`

**Interfaces:**
- Produces: after every sentinel pass (market open or closed — the heartbeat proves the *scheduler* is alive, so record it unconditionally in the job), write `observations.add("heartbeat", "sentinel pass")`… **No** — observations is an append-only journal consumed by consolidation; a row per hour forever is pollution. Instead: a single-row table approach via `rule_states`-style upsert is also wrong-shaped. Use a new tiny key-value: `conn.execute("INSERT INTO app_state(key, value) VALUES('sentinel_last_pass', ?) One row, overwritten hourly; invisible to consolidation.

Steps:
- [ ] Migration + failing store-level test for the upsert (two writes, one row, latest value).
- [ ] Failing scheduler test: driving the job via the existing FakeScheduler records a heartbeat even when `is_market_hours()` is False (patch the clock per the established pattern — this suite already burned once on an unpatched clock).
